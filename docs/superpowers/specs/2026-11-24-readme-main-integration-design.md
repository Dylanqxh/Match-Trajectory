# README 与主分支集成设计

## 意图

让第一次打开仓库的访问者在几分钟内理解 Match-Trajectory 解决什么问题、如何启动、当前工作流是什么，以及哪些结果仍需人工核对；随后把已经完成并验证的工作流 UX 改动合并到默认分支 `main`。

## 目标

- README 先说明产品价值与适用边界，再给出可直接复制的启动命令。
- Windows 已配置开发环境与跨平台 Docker 两条启动路径都容易找到，并明确各自前提。
- 使用流程与当前三阶段界面一致：材料采集、独立生成工作区、文档工作区。
- 写清双材料入口、三种文档视图、证据边界、本地存储与模型连接方式。
- 开发验证命令覆盖布局、前端测试、类型检查、构建和后端测试。
- 保留现有媒体引用原文，不查看、不生成、不修改图片、音频或视频资源。
- 只合并到本地 `main`，不推送远端。

## 非目标

- 不修改产品功能、接口、依赖或现有媒体资源。
- 不把合成测试或自动化测试表述成真实用户效果验证。
- 不承诺模型生成内容绝对正确，也不把第三方中转写成官方服务。
- 不暂存或修改工作区中未跟踪的用户文档。

## 方案比较

### 方案 A：在现有 README 上重排并补齐（采用）

保留现有徽章、媒体引用、架构图和已有技术说明，重写信息层级与当前工作流。改动集中，历史信息损失最小，也最符合本次“优化 README”的范围。

### 方案 B：改成纯产品落地页

更适合展示，但会弱化自部署、开发验证和安全边界，不利于开源仓库首次使用。放弃。

### 方案 C：改成纯开发手册

启动最直接，但无法解释产品价值、证据规则和用户工作流。放弃。

## 信息结构

1. 一句话定位、当前成熟度和适用范围。
2. 保留现有徽章与媒体引用。
3. “快速启动”同时提供 Windows 已配置环境和 Docker Compose。
4. “第一次使用”按材料、生成、编辑核对导出的阶段描述当前界面。
5. “核心能力”解释双入口、证据驱动、岗位 Skill、版本与导出、本地优先。
6. “能力边界”集中说明人工核对、文件解析、模型连接和真实效果边界。
7. 模型连接、数据安全、开发验证、设计文档与许可证作为维护者信息保留。

## 验收

- README 中的命令、脚本名、端口、支持的协议和文档链接均能在仓库中找到对应实现。
- README 不新增或修改任何媒体引用及媒体文件。
- README 不再把材料采集、生成进度和文档编辑描述为同一拥挤页面。
- README 明确 `npm run test:layout`，并给出完整的前后端验证命令。
- 功能分支提交后，本地 `main` 使用 `--ff-only` 合并并通过完整回归。
