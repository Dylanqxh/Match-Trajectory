## 1. 好简历是什么

> **在真实经历的边界内，让招聘方快速看清：为什么适合这个方向、本人做成过什么、有什么值得进一步了解。**

“适配＋优秀”是表达目标；可信是底线，易读让价值被看见。没有竞争者数据时，不宣称用户领先其他人。

| 判断 | 应体现什么 | 应避免什么 |
| --- | --- | --- |
| 适配 | 相关能力在经历、项目或作品中有所体现 | 只有岗位关键词 |
| 贡献 | 本人动作、责任范围和交付明确 | 把团队成果全算给个人 |
| 亮点 | 方法、判断、约束、质量或结果有依据 | 堆工具、空泛夸奖、编数字 |
| 易读 | 重点靠前，表达简短，术语有上下文 | 流水账、重复卖点、过量加粗 |

数字、名企和复杂技术不是必选项。接口、实验、需求方案、内容作品及有效反馈，都可能提供证据；缺少结果时写清已有动作，不补“效果显著”。

上述原则参考 [Harvard](https://careerservices.fas.harvard.edu/resources/create-a-strong-resume/) 与 [MIT](https://capd.mit.edu/resources/resumes/) 职业指导；海外格式习惯不直接作为中文求职硬规则。

**选择一份通用 Skill，按需组合岗位规则。** 统一事实与写作标准，岗位差异放入参考文件；避免一份巨型提示词，也避免五套互相重复的流程。

当前运行结构如下；宿主按岗位、求职背景与执行阶段加载，并随任务冻结内容与资源清单：

  references/review-boundaries.md  # 审阅误判边界

  references/candidates/entry.md   # 校招
  references/candidates/experienced.md # 社招
  references/candidates/transition.md # 转岗
  references/candidates/returning.md  # 可叠加的空窗规则
  references/evidence/common.md    # 课程、研究、工作、作品等写法

入口优先呈现选材、贡献表达、证据与自检，控制篇幅；字段和误判细节放入参考。默认加载一个主方向，必要时补经历写法；不一次加载全部岗位和例子。岗位画像由应用提供，个人资料不写进 Skill，评测答案不进入生成上下文。

## 3. 通用规则：选择、表达、追问

### 选择什么

先选与目标直接相关、个人贡献具体的经历，再补可迁移能力；压缩重复和无关内容。保留必要任职时间线，不因裁剪造成虚假印象。

每个卖点保留简短映射：**目标关注点 → 事实 ID → 本人动作 → 支撑的表达 → 未知项。** 不使用未经验证的精确打分权重。

没有 JD 时使用应用提供的岗位画像；有 JD 时区分明确要求与通用关注点。用户不填公司职级，系统也不推断。目标岗位和示例不能提供用户的个人事实。

### 怎样写

按需要组合“任务背景、本人动作、方法、结果或交付”，缺哪项就省略哪项；不强制每段凑齐固定结构。项目可先用一句话交代用途和本人范围，再写少量具体条目。

板块按证据价值安排，板块内部保持清楚的时间顺序；不按固定工作年限套模板。技能必须有用户陈述或实践依据，“用过”不能自动升级为“精通”。

亮点来自真实方法、取舍、约束和成果；突出用户能够展开说明的细节，作为面试讨论入口。不制造技术难点或悬念。

### 何时问

优先问会改变核心段落的问题，例如“你本人完成了哪一步”“最后交付了什么”。不要求用户自己总结专业亮点。

首次最多一轮、三个问题，岗位方向澄清也占用该预算。用户跳过后立即按已知内容生成。只有目标、没有个人事实时，交付明确标识的框架与最低补充入口，不计为可用简历。

## 4. 岗位规则：改变证据重点，不改变事实

| 方向 | 优先回答 | 需要保留的边界 |
| --- | --- | --- |
| 后端研发 | 做了哪个模块，如何解决问题，怎样验证？ | 课程／测试／线上环境、测试规模／业务规模分开 |
| 算法 | 任务、数据、评价与对比是什么，本人贡献是什么？ | 指标口径、离线／线上、复现／创新、在投／发表分开 |
| 数据分析 | 用什么数据回答什么问题，结论支撑什么行动？ | 相关／因果、提出建议／被采用、报表／业务收益分开 |
| 产品经理 | 为什么做、如何取舍、推动哪一步、交付反馈是什么？ | 建议、评审、发布和效果验证分开 |
| 内容／用户运营 | 面向谁、在哪个渠道、做了什么、反馈口径是什么？ | 曝光、点击、报名、付费及团队／个人结果分开 |

算法包含通用实验规则，并用推荐／搜索、NLP、计算机视觉案例验证差异；不等同于大模型岗位，不要求人人有论文或部署经验。其他岗位尚未专项验证时，明确提示并回退通用规则。

**边界示例，来自本地构造案例 C02：** 已知本人用事件 ID 与数据库唯一约束处理重复消息；同一事件重放 100 条测试消息，仅更新一次状态。

- 可写：“使用事件 ID 与数据库唯一约束处理重复消息；同一事件重放 100 条测试消息，状态仅更新一次。”
- 不可写：“构建高可用架构，支撑百万级消息并保障高并发稳定性。”输入没有这些责任、规模和效果。

非技术经历采用相同原则：把“做过活动”具体化到真实排期、内容、沟通或数据记录，不能直接升级为“搭建增长体系”。

## 5. 调用契约：同一 Skill，分阶段工作

公共输入：`stage`、目标依据、可用事实及原文来源、规则版本、剩余追问预算；同时携带相关否定、责任限制与更正，避免选材时丢掉边界。修改时追加当前简历版本与目标段落。联系人等无关信息由本地回填。

| 阶段 | 负责什么 | 必须返回 |
| --- | --- | --- |
| plan | 选材、安排重点、判断是否追问 | `decision: ask/draft`、选材与简短依据、问题、未知项 |
| draft | 根据事实生成可编辑正文 | 有序板块、段落 ID、正文、`fact_ids`、待确认项 |
| review | 独立上下文对照原文审查 | 问题位置、类型、严重程度与修正建议；无问题也明确返回 |
| revise | 根据用户指令或宿主接受的审查意见局部修改 | `base_revision`、目标段落、补丁、引用与修改理由 |

review 读取本轮事实、对应原文、限制条件、目标依据和候选稿，不读起草者的自评或选材理由。来源片段由程序从原材料定位，不用模型自己生成的“原文”证明事实抽取正确。审查意见不能自动确认新事实；`fact_ids` 指向不可变的事实修订，版本失效规则由 Agent 管理。

所有事实性陈述须能追溯当前输入，包括教育、任职、技能和经历。普通用户陈述可用于起草，不等于系统客观核实。待确认仅用于已有歧义或用户提出的事实变更，不能先编经历再让用户默认确认。

JSON Schema、引用存在性、版本冲突、预算、工具权限和文件导出由宿主控制；Skill 不自行保存、无限循环或重置预算。宿主如何注入规则与执行阶段，见 [Agent 方案](简历Agent架构设计方案.md)。

## 6. 材料不足与质量检查

| 情况 | 应怎样处理 |
| --- | --- |
| 缺本人动作 | 优先询问；跳过后只保留已知参与范围 |
| 缺成果数字 | 写已有动作和交付，不补百分比或定性成功 |
| 数字缺口径 | 不擅自计算提升比例或扩大结论；必要时待确认 |
| 来源冲突 | 暂不采用有争议说法，指出具体冲突 |
| 用户要求“高级一点” | 优化结构与术语；事实范围变化须用户明确确认 |
| 修改一个段落 | 保留其他内容，只联动实际受影响的段落 |

问题分三类：**阻断**是无依据事实、冲突或错误归属；**提醒**是证据不足、材料不完整或岗位差距；**建议**是结构与措辞。缺数字不自动阻断，真实差距不靠包装消除。

事实 ID 有效不等于语义成立；仍需检查原文是否支持整句话。用户能否解释主要内容，由真实试用验证，模型不能代替本人确认。

审阅可能误判。用户可引用已有原文并说明异议，保留原问题与处理依据；不能仅点击忽略来清除阻断。无需改造真实经历或编造新事实，处理路径见 Agent 方案的手工核对规则。

## 7. 怎样验证这份 Skill

先记录无 Skill 的基线，再编写最小规则，用相同输入、模型和可比预算做对照。只针对观察到的失败补规则；不把参考答案或隐藏事实提供给生成模型。

测试采用产品方案计划的 40 个基础场景及反例，覆盖五方向、校招／社招、完整／稀疏材料、有／无 JD。重点检查同材料换目标、算法评价与论文状态、团队归属、无数字表达、局部修改和停止条件；关键场景至少重复三次，并用保留案例检验泛化。

各方向审阅者依据**当次可见输入**裁决，不能要求稀疏稿使用隐藏事实。每例预先标注可采用的核心贡献和禁止扩写范围，允许不同合理写法；有直接相关核心证据却全部遗漏、只替换岗位关键词，或相关性／贡献被判为 0 的案例须修复复测，否则该方向不能标为专项验证通过。没有相应证据时按不适用处理，不倒逼模型编造。

增加两类反例：抽取时漏掉“仅参与／未上线”等限制；模型误判个人贡献、用户引用已有原文提出异议。分别检查边界是否保留、错误阻断是否有处理出口。

事实扩写单独判定，不能被文风高分抵消。其余按相关性、贡献、证据和结构给出有理由的 0／1／2／不适用判断。记录加载资料、调用量、耗时、失败和人工修改；真实可用率以产品试用为准，不将自评分换算成“80% 可用”。

当前主 Agent 仍一次独立审阅，同时返回事实结论与四维质量报告，不增加每轮模型请求。每项包含0／1／2／不适用、理由、正文位置、原文引用和改进动作；缺证据与可修正表达分别处理，质量状态由动作校验，事实通过不等于质量通过。

五组全新上下文的探索性指令对照没有观察到明显虚构，部分场景展示了相关经历优先与追问取舍；两组都能写出合理内容，不能据此宣称 Skill 有稳定增益。教学正反例与试验输入分开，试验报告不注入生成上下文。真实供应商重复对照、40场景、行业审阅和用户可用率验证仍待实施。
