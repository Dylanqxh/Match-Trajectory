# 选材、压缩与版面表达

## 先确定读者应记住什么

选材与起草之前，确定本次目标的 2—3 项核心能力；各找一条有本人动作或交付的证据。没有证据就标为缺口，不靠关键词补齐。
选择最能证明这些能力的经历，避免按材料出现顺序或纯时间倒序逐句改写。一个经历只保留不同的贡献。摘要、项目、技能不要反复介绍同一件事。

先在内部形成 `核心能力 → fact_id → 本人动作 → 方法／判断 → 交付／验证 → 未知项` 的短映射。共同支撑同一目标的动作只有在原文明确存在依赖时才连接；同公司、同项目或相邻出现不足以证明数据流、闭环或因果。最终正文不展示这张映射，但每个元数据和条目都要保留实际支持它的 fact_ids。

## 信息结构

- 姓名、联系方式、目标由宿主填写，不放入生成正文，也不要从原文里挑一个邮箱填进页眉。
- fixed_education 非空时，教育由宿主原样回填。即使用户填写的学校和原文全称不一致，也用用户填写的，不要改名、改专业、改学历。
- 用户没填学校时，education.school 只能是原文里的学校全称，不能缩成更短的校名。
- 没有固定教育、原文也没有校名时，school 留空。仅说「双一流高校」不能编出校名。
- kind 只能是 skills、project、work、campus。title 写这段经历自己的名称，不要拿「校 ACM 集训队」当一级标题。
- 项目名称未提供时可用任务用途做中性标题，不能命名成原文不存在的商业产品。
- 起止日期仅取自对应经历的原文，格式 YYYY 或 YYYY-MM。同一段经历的标题日期和条目里的时间必须一致。不能用「前段时间」、学历或相邻项目反推时间。
- 项目和 work 按 JD 相关度与证据强度排序，日期只在强度相同时倒序。没有内容的块不要输出。
- 每个 section 的 fact_ids 支撑标题、组织、角色与日期；正文每条仍各自引用。

## 起草预算：优先一页可扫读

- 校招不写简介。社招或转岗需要时只写 1 句、通常不超过 60 字，写方向和已有实践，不写求职意愿，不把技能清单再抄一遍。
- 每段核心经历通常 2—4 条；材料少时 1 条也可以。每条优先 40—90 字，原则上不超过 110 字。
- 每条集中表达一项贡献：**本人动作＋关键方法／判断＋可核对的交付／验证或原文结果**。
- Owner、0→1、端到端、全链路只在原文同时支持角色、起点和实际覆盖范围且有表达价值时使用；优先写清具体贡献，不用标签代替证据。
- 原文里的获评、名次、获奖和明确数字必须出现在正文里。没有结果数字时写交付物或验证方式。
- 负面和无关事实默认不写：已下线、未推广、试运行后停止、某部分由其他成员完成。可省略，也可压成「本人负责 X」。不得改成上线、全校、生产或独立完成。
- 技能通常 2—4 条短句，按 JD 里的能力顺序，写清「熟悉／使用过／了解」。了解不能写成熟悉，Spring 不能写成 Spring Boot，一项实践不能写成两个项目。
- 与 JD 无关、只跑过一次的工具可以不写，不能升级。
- 用户说「提升明显」但未给数值时，写评估口径和已交付记录，不写成确定的量化突破。

## 有节制地突出重点

正文 items.highlights 可选，每条最多 2 个原文短语，每处不超过 30 字；通常选一个关键方案或交付，不能整句加粗。
短语必须逐字出现在该条 text 中。优先突出能展开的方法或交付，而不是「优秀」「自主设计」这类评价词。评价词本身如果是原文结果，要写进正文，但不靠加粗代替事实。

## 追问被跳过

仍按已有证据写满每一个有材料的块。不要因为跳过而删掉项目、获奖或数量结果，也不要输出空块。
某一条已经存在、但缺关键事实时，在该条末尾加 `【待补充：…】`。两个口径冲突时加 `【待确认：…】`，不要擅自选一个数字或日期。

## 审阅与修正

先查事实，再查目标能力、本人贡献和原文结果是否还在；最后查长度、重复、空话和重点。
质量问题用 warning：指出具体条目以及删什么、保留什么。缺时间、缺数字、段落长本身不是事实错误。
压缩时可以删掉负面句和无关句，但不能补新技术、日期或成果，不能把状态、范围或规模写强，不能移动未点名的经历。保留稳定 ID 和引用。
达到预算仍有建议时交付带提醒的草稿，不能无限修正。
