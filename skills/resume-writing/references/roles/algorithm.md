# 算法／Agent／RAG

本文件是维护的通用关注点，不是实时JD，也不是个人事实。

| 招聘方关注 | 原文找什么 | 怎样写 |
| --- | --- | --- |
| 解决什么任务 | 问题、数据来源、本人方法或实验 | 先写任务与改动，再写工具 |
| 如何证明方法有效 | 基线、评价口径、误例与对照记录 | 说明比较什么、按什么评价、交付什么；缺数值可写实验与脚本 |
| Agent／RAG是否形成闭环 | 任务拆分、检索／工具作用、输出校验、可运行产物 | 围绕一个真实任务写链路和验证，避免只列模块名 |
| 是否可复现与落地 | 数据处理、运行脚本、接口、已知使用范围 | 区分复现／创新、离线／线上、原型／内部试用／正式上线 |

## 选材顺序

先直接相关贡献，再可迁移方法与作品，最后保留必要背景；核心条目突出一个可以展开的方法或交付。没有该类证据就保留真实差距。

## 常见误写

实验没有上线或没有准确率时，不要补这些结论。负面边界可以不写进正文，但不能改成已部署或已发表。

阅读论文不等于成果；LoRA实验不等于训练基础模型；只有向量数据库接触或求职目标不能写成RAG项目。推荐／搜索看样本与排序验证，NLP看任务与约束，视觉看数据与标注。论文和部署都不是必填。

## 怎样选一条算法经历

先判断这是推荐、搜索、NLP、视觉、Agent 还是传统机器学习，依据是本人实际做的任务，不是公司名字。岗位名称保持原文：算法实习生不能改成算法工程师。

一条值得展开的经历，按这个顺序取材，缺的环节就留空，不要补：

1. 任务和约束：要解决什么，数据从哪来，评测或上线限制是什么。
2. 本人改动：改了采样、特征、损失、检索、提示或评测脚本中的哪一步。同组其他人维护的流水线单独说边界。
3. 技术关系：这一步依赖上游特征，还是和另一条实验并行，还是只为对照而补充。相邻写在一段里，不等于数据流。
4. 验证范围：数据集或任务名、离线还是线上、基线是什么。全系统收益不能写成这个组件的收益。
5. 结果：只保留材料里的对照数字，并带上口径。没有准确率、没有上线，就写到实验记录为止。

论文和竞赛可以是强信号。写清论文题目或赛事、作者位次、团队名次和本人负责的部分。第二作者不能写成第一作者或独立完成；团队第 2 名不能写成个人第 2 名。阅读论文、复现教程、只接触向量库，都不能写成已发表或已落地的 RAG。

专业技能按实验里真实用过的库分组，例如「离线评测：Python，用于材料中的召回对照」。不要把 xxxx 换成一套没写过的框架。

## 写法示例

材料只说「在课程点击子集上把随机负样本改成同会话未点击，离线 Recall@50 从 0.31 到 0.36，特征平台不是本人维护」时，可以写成：在课程点击子集上调整负采样，并用随机负样本做离线对照，Recall@50 从 0.31 到 0.36；特征平台由他人维护。不能写成：负责推荐系统，线上点击率提升 20%，精通 PyTorch。
