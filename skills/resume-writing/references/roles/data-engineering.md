# 数据开发／数据工程

本文件是维护的通用关注点，不是实时 JD，也不是个人事实。选材围绕数据从哪里来、如何处理、怎样核对、如何稳定交付；原文没有的规模、时延、吞吐、生产等级和个人责任不得补写。

| 招聘方关注 | 原文找什么 | 怎样写 |
| --- | --- | --- |
| 数据链路是否完整 | 数据源、采集方式、同步／入湖／入仓、下游用途 | 按“来源—处理—校验—交付”写清本人动作 |
| 口径与质量怎样保证 | 对账、去重、补数、异常检测、监控告警 | 保留配置对账、校验规则和告警治理等原文强事实 |
| 工程可靠性 | 灰度、回滚、失败重试、任务依赖、故障处理 | 只写材料明确发生过的机制和范围，不把了解写成生产实践 |
| 数据与平台技术 | SQL、数据库、消息、批流处理、调度工具 | 工具必须绑定具体任务；原文的熟悉／掌握程度不得擅自升降 |
| 交付与协作 | 方案、开发、测试、上线、文档、跨团队核对 | 写清交付物和个人边界，保留“能独立完成”等有依据的表述 |

## 选材顺序

优先选择与目标 JD 数据链路最接近、且包含校验或交付闭环的经历；再放平台工程、数据库和后端实践。只有工具罗列、没有任务上下文的内容放在专业技能，不扩写成项目成果。

## 常见误写

离线入湖不能自动写成实时数仓，配置对账不能泛化成数据治理体系，接触 Binlog 或 OMS 不等于主导 CDC 平台。原文写“掌握分库分表基本原理”就保留该程度，不降为“了解”，也不升级为“精通分布式架构”。没有给出数据量、延迟、成功率时不编指标。

## 同材料对照
